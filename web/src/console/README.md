# Niadra Console

The interface of the people who govern the memory: security and privacy, integration, review and the
leadership that follows the numbers. **It is not a customer service screen.** No screen shows a queue of customers waiting, a
conversation in progress or a box to reply. Clientes lists the customers the memory knows, by pseudonym, to
inspect one: nobody is served from it. A conversation only appears as evidence: in a receipt,
in the lineage, in the measurement, in a review sample.

It lives inside the site (`web/`), at `/console`, with its own shell, and is loaded only
when someone opens `/console` (file `ConsoleApp-*.js`, about 53 KB with gzip).

## Runtime configuration: `/config.json`

The Console reads `/config.json`, next to `index.html`, every time it opens. No address
lives in the code.

```json
{
  "controlURL": "https://control.<ip>.sslip.io",
  "apiURL": "https://api.<ip>.sslip.io",
  "cells": { "<cell_id or region>": "https://..." }
}
```

| Field | Required | What it is |
|---|---|---|
| `controlURL` | yes | Control plane (`niadra-control`): login, token, projects, sources, keys, configuration, usage |
| `apiURL` | if there is no `cells` | Data API of the cell (`niadra-admin`), used by default |
| `cells` | no | Address per `cell_id` or per region, for spaces served by another cell |

The data API of a space is `cells[space.cell_id]`, then `cells[space.region]`, then
`apiURL`. Every address needs `https`; `http` only works for `localhost` and `127.0.0.1`.
With no file, or with an invalid file, the Console shows the reason instead of a blank screen.

To generate the file from the environment:

```sh
NIADRA_CONTROL_URL=https://control.<ip>.sslip.io \
NIADRA_API_URL=https://api.<ip>.sslip.io \
sh deploy/console-config.sh dist/config.json
```

`NIADRA_CELLS="cell-eu-1=https://...,eu-west-1=https://..."` is optional.

### What the web server needs to do

- Serve `console.html` (generated by the prerender, empty `#root`, `noindex`) at `/console`
  and at `/console/*`. The `deploy/Caddyfile` of the site image already does this.
- Allow the origins of `controlURL` and of the data API in the CSP `connect-src`. In the image,
  `deploy/entrypoint.sh` builds the list from the environment.
- Serve `/config.json` without cache. In the image it is written on start, outside the site folder.
- The control plane and the data API need to answer CORS for the Console's origin
  (`Authorization`, `Content-Type` and `Idempotency-Key` in the allowed headers).

## Session

- Sign-in starts with the e-mail. `POST {controlURL}/v1/auth/sso/discover` says, by domain only, whether it
  signs in through the tenant's SSO (it never says whether a person exists). An SSO domain gets "Entrar com
  SSO"; when the tenant enforces SSO, the password stays only for tenant-wide admins, as the way in when the
  identity provider fails. Other domains get the password field.
- Password: `POST /v1/auth/login` with `{email, password, totp?}`. If the account has a second factor, the
  first attempt comes back 401 `invalid second factor` and the code field appears. 401 `second factor
  enrollment required` starts the setup in three steps: connect the app (`POST /v1/auth/second-factor` gives
  the secret for the QR code), confirm the first code, and keep the ten recovery codes that the confirming
  login returns once (`recovery_codes`), with a .txt download, a copy button and a required "Guardei os
  códigos num lugar seguro".
- SSO (OIDC or SAML 2.0): the Console draws a random value, sends only its SHA-256 to
  `POST /v1/auth/sso/start`, keeps the value in this tab's `sessionStorage` and goes to the provider. The
  provider answers the control plane, which sends the browser back to `/console/sso` with a one-time sign-in
  code in the URL fragment (never sent to a server). The Console removes the fragment and the kept value at
  once and exchanges both at `POST /v1/auth/sso/exchange`. The kept value is the one thing the Console ever
  puts in browser storage: it is not a credential, it never holds a token, and it lives for one trip to the
  provider. When the tenant asks for the Niadra second factor on top of the provider's, the same code steps
  follow, with `POST /v1/auth/sso/second-factor` for the enrollment.
- A person who lost the app sends `recovery_code` in place of `totp` (never both). Each code works
  once; the answer says how many remain (`recovery_codes_left`) and the Console points to the
  account page. The codes, like the token, never reach browser storage.
- The answer is `{access_token, expires_in, space_id}`: a person JWT with the space as
  audience. The Console reads the claims (`tenant`, `space`, `region`, `env`, `roles`, `sources`,
  `exp`) only to display and to schedule; the server is what verifies. The same token works on the
  control plane and on the data API.
- Switching spaces and renewing use `POST {controlURL}/v1/auth/token` with `{space_id}`. The
  renewal happens one minute before `exp`; if it fails, the session ends at `exp`.
- The token stays only in the tab's memory. Nothing goes to `localStorage`, `sessionStorage`, a
  cookie or the URL; reloading the page asks for the login again. A test checks it.
- A 401 on a call made with a token ends the session and goes back to the login with a notice. A deactivated
  person gets that 401 at the next call to the control plane.
- An invitation link, `/console/convite#<token>`, lets a new person choose a password
  (`POST /v1/auth/invitation/preview`, then `POST /v1/auth/invitation`); the token leaves the address bar at
  once and travels only in bodies. The login that follows sets up the authenticator.

The data subject's file (`POST /v1/export`) comes back with a presigned `download_url` to the
object storage, which the browser may not reach (in the sandbox it does not). The
Console ignores that link and downloads through `GET /v1/exports/{run_id}/download`, with the
session token. The file holds the subject's data decrypted, so it lives 24 hours (`app/privacy.py`,
`PACKAGE_TTL`): after that the download answers 404 and the file leaves storage, and an erasure that
reaches the subject deletes its files at once. The Console says so where the file is asked for and
when it is ready, turns that 404 into "passou das 24 horas ou saiu com um apagamento", and shows each
file among the export runs (`schedule_id` `on_demand`) with its expiry or deletion, from the run's
manifest. `download_expires_at` is the presigned link's 15 minutes, which the Console does not show.

A new continuous export schedule is typed in a form on the Data screen, never as JSON. The entry has the
fields of `ExportSchedule` (config/models.py): kind `s3`, the space's region (the control plane refuses
another one, and a second schedule on the same bucket and prefix), the chosen tables, `pseudonymize` when the
person asks for it (the `handles` table then leaves out each value and keeps its keyed hash; the other tables
go as they are), and the credential reference `spaces/<space>/export/<schedule>`, like every secret of the
cell. Right before sending, the Console
reads the document again and appends the entry to it, so a change approved meanwhile is kept, then sends it
as a diff with a reason, which waits for approval in Configuration (four eyes; the author approves alone
only in a tenant with one admin). The destination credential is typed as the two halves of an access key
and goes to the vault as the JSON the S3 destination reads.

A webhook endpoint is added from Systems, on the source that receives it: the Console draws a Standard
Webhooks secret (`whsec_` and 32 random bytes), writes it straight into the cell vault, registers its version
on the control plane (`spaces/<space>/webhook/<endpoint>`, like every secret of the cell) and proposes the
endpoint as a diff with the event types the cell sends. The secret is shown once, for the receiving system.
It takes the Security role (the vault) and a role that writes `webhook-endpoints`; the Administration has both.

A SIEM stream is added from Systems too, in "Comprovantes no SIEM", with the same steps and the same roles: the
Console draws the signing secret, writes it into the cell vault, registers its version and proposes the
stream as a diff of the document read again right before sending. The stream is an entry of
`webhook-endpoints` with `format` `ocsf` (OCSF 1.3, one API Activity event per line) or `hec` (the same event
in an HTTP Event Collector envelope), `event_types` with the receipt kinds or `*`, and the source that owns it
(the stream carries the receipts of the whole space). An optional collector token goes to the vault as the
whole `Authorization` value (`Splunk <token>`, `Bearer <token>` or the value as typed) at
`spaces/<space>/webhook/<endpoint>-token`, named by `authorization_ref`, registered with the kind
`collector_token`, and never comes back to the screen. Either form refuses an id whose secret another
endpoint already names, since the vault reads the latest version and writing it again would replace that
endpoint's secret. Each stream links to its deliveries in Alerts, where a failed or dead one is sent again by
hand (`POST /v1/webhooks/deliveries/{id}/redeliver`). A stream never appears among the endpoints that receive
warnings, nor among the endpoints a warning rule can choose.

Warning rules (Alerts, "Criar e testar") and pattern rules (Patterns) are built from the catalog too, never
as JSON. A new rule takes an id from the condition or the catalog entry, free in the document; a rule in use
comes in from "Regras em uso" with its values, keeps its id and goes out with the next version (`v2` becomes
`v3`), and the parameters the form does not edit go back as they were. The rule is sent only after a test of
the exact draft, and a warning the endpoint could not receive is not sent at all. Turning a rule off or on is a
diff too. The control plane checks the documents again when the diff arrives and when it is approved
(`app/control_config.py`), and the Console puts its refusals in words (`lib/configProblems.ts`). The server's `detail` is English for developers and never reaches the screen as it came: `api/describe.ts` says the known ones in words, with the next step, and an unknown one becomes the sentence of its code, with the request id kept for support.

A read the server asks to try later (a 503, when the region is busy or a space is still being prepared, or
a 429) waits for its `Retry-After` and tries again by itself, up to 30 times (`lib/useResource.ts`); the
screen shows a wait with the seconds left and "Tentar agora", never a failure. An action (a search, a
diff, a key) is not repeated by itself: its error says how long to wait. The control plane and the cells
expose `Retry-After` through CORS for this.

The identity writes and the erasure send `Idempotency-Key`, which the server requires;
the key writes and the cut send it too, for safety. A customer identifier (phone,
e-mail, ID) only goes in the body; a test with a canary value checks every URL. A conversation id is treated
the same way, since a channel's conversation id may be a phone number or an e-mail: the receipts search, the
measurement of one conversation and the erasure of one conversation carry it in the body, and the receipts
filter keeps it in the router state. `test/conversation-ids.test.tsx` fails if one reaches a fetched URL or
the address bar, or if a client call puts one in a path or a query string.

A sandbox space shows, on every screen, "Sandbox: apenas dados sintéticos", and the tab
title starts with `[Sandbox]`.

## Roles

The roles are the control plane's: `admin`, `security`, `integration`, `review`,
`analysis` and `vendor`. `admin` passes every server check. The Console hides what the
role cannot do (for example, the cut requires `security`; usage per agent, `analysis`),
but the server is what decides.

## Run and verify

```sh
npm test               # vitest + Testing Library, simulated fetch (src/console/test)
npx tsc --noEmit -p .
npm run build          # the whole site, with the prerender and console.html
```

`test/copy.test.ts` reads every file of the Console and fails on an en dash or an em dash, and on a promise
that a sample review verdict moves a limit or changes memory: a verdict counts in the agreement, runs as a
test case and corrects the count it judges, and changes nothing else.

For `npm run dev`, create `public/config.json` only on your machine (do not commit it):
`{ "controlURL": "http://localhost:8080", "apiURL": "http://localhost:8000" }`.

## Design decisions

Reading: a governance console for security, privacy,
integration and review; ENERGY 1, RHYTHM 2, MOTION 1.

- **Agno's dashboard structure** (rail on the left with the selector on top, 14px body,
  data in 12px mono, 36px controls on desktop and 44px on touch), studied in
  `agno-agi/agent-ui` (MIT). No code copied.
- **Dark rail grouped by the job to be done**, not by module (`lib/screens.ts` `NAV_GROUPS`): Clientes e
  memória; O que os agentes fizeram; Privacidade e direitos; Conexões; Avançado (the technical screens,
  closed until the person opens it or lands on one of them, remembered in `localStorage`); Administração.
  Each group says its job in one line under its name.
- **One registry for every screen** (`lib/screens.ts` `SCREENS`): the name, the job in one line, the line
  under the title, and the help that "Ajuda desta tela" opens from the rail (`ui/HelpDialog.tsx`: what the
  screen is, how to read each part, the one thing to do there and its words). `PageHeader screen="..."`
  renders the name and the line under it, nothing more: the screens carry no instructions of their own, and
  the teaching lives in that help and in the Tutoriais (founder, 10/10/2026). A term of art shows with its
  definition one tap away (`ui/Term.tsx`, from `lib/glossary.ts`), by hover, focus or click, closed with
  Escape.
- **The words are the glossary's**: comprovante, never recibo (the address `/recibos` stays);
  agente, never bot. `test/copy.test.ts` fails on either.
- **Início** (`/e/:space/inicio`, the first screen of a space) opens on the tutorials, then three tiles of what
  the memory is already doing, each a link to the screen behind it and answered Sim, Ainda não or Não
  conferido from what the space records: agents connected (the live sources, and for the Administration the
  keys of the first five), events arriving (in 90 days, from `GET /v1/sources/arrived`, which every role may
  read) and context delivered (a receipt of a read). Nothing there is a task: while no agent is connected, the
  one manual act, a key, is offered under the tiles. Then the jobs of the Console. A read the role cannot make
  says "Não conferido" instead of guessing.
- **Tutoriais** (`/e/:space/tutoriais`, `lib/tutorials.ts`): one guided walkthrough per job, eight in all. A
  step names the screen and the part of it (a `data-tour` anchor); "Começar" and "Me leve lá" open that
  screen with the guide (`ui/TutorialPlayer.tsx`) beside it, which highlights the anchor, follows the person
  from screen to screen (the run lives in `sessionStorage`), waits on a detail screen for an item to be
  opened, and records the walkthrough as done per person on the control plane
  (`GET /v1/users/me/preferences`, `PUT /v1/users/me/preferences/{key}`, keys `tutorials` and `welcome_seen`),
  so the progress follows the person to another browser; `localStorage` keeps a copy that the screens read
  and that stands alone when the control plane does not answer (`lib/tutorialProgress.ts`). The welcome, once
  per person, offers the five-minute tour; "Ajuda desta tela", in the rail and on the phone's
  bar, opens the help of the current screen and the walkthroughs that pass through it.
- **Origin stamp in mono** on every memory item: agent, channel, type, time.
- **"O contexto que o agente recebe" next to the memory**, with the effect of the policy on each
  item and what was withheld, by reason.
- **Masked content appears as masked**, and what the role's policy denies appears
  only as a count per reason: the screen never pretends the item does not exist.
- **One red (`#b42318`)** for destructive actions, overdue and error; the rest is the site's palette.
- **Every data view has loading, empty and error**, and the error shows the request code.
- **Every governance write asks for a reason when the server keeps a reason**, and the reason
  goes to the receipt.

## Console gaps

- A deactivated person is refused by the control plane at the next call, but a token already issued keeps
  working on the data API until it expires (15 minutes at most): the cells verify tokens offline.
- SCIM provisioning is not there: people come by invitation or just in time through the SSO.
- An SSO domain is claimed without a DNS check; tenants are created only by Niadra, under contract.
- An endpoint or a SIEM stream is added from Systems, but rotating its signing secret (two secrets during the
  rotation) and turning it off are still a JSON diff in Configuration; a new collector token is written in
  Configuração, Segredos, as the whole `Authorization` value under the id `<endpoint>-token`.
- The Caddy `@console` block and the Docker image were not run on this machine.
- A receipt older than `person_label` (written before the cell kept the names) shows the person's id until that person acts again in the space.
